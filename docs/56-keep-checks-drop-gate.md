### 代码改动

#### 1. 去掉阻断（`MainActivity.smali` L7389）

检查弹窗里 `v2` 统计所有失败项数，原逻辑：

```smali
if-lez v2, :cond_4    # 没有失败项 -> 走允许分支；否则走阻断分支
```

改为无条件跳转到允许分支：

```smali
goto :cond_4          # 无论检查结果如何，都走「允许打开」路径
```

**效果**：弹窗仍完整展示所有检查项（红绿状态），但不再阻止开启。允许分支会显示：
- 全部通过 → 「全部通过，正在打开。」
- 必需项通过、部分可选项失败 → 「必需项全部通过，正在打开；N 项只影响对应功能。」

#### 2. 修复 LSPosed 版本比较（`C.smali` L1278/1284 + `C.java` L72）

**原逻辑**（精确相等）：

```java
boolean z2 = z && i2 == 102 && j == 7912 && str != null && str.contains(f);
```

**问题**：设备实际 LSPosed 是 `2.2.1 / 7939 / API 102`，build 号 7939 ≠ 7912，被误判为失败。弹窗显示自相矛盾的「2.2.1/7939/API 102，需要 2.2.1/7912/API 102」。

**修复**（大于等于）：

```java
boolean z2 = z && i2 >= 102 && j >= 7912 && str != null && str.contains(f);
```

smali 对应：

```smali
if-ne v2, v10, :cond_4   →  if-lt v2, v10, :cond_4    # API >= 102
if-nez v10, :cond_4      →  if-ltz v10, :cond_4       # build >= 7912
```

**效果**：诊断信息里 LSPosed 显示「已连接 · 2.2.1」（绿色）。这个修复同时作用于「打开前检查」和「诊断信息」两处。

## 关于 Root 检查失败的说明

测试中「打开前检查」显示 Root 为红：

```
Root
没有 su，或被拒绝。打开 KernelSU → 超级用户（应用授权）→ 找到 MiDuo → 打开允许，回到 MiDuo 再点一次开关
```

但通过 adb 验证 `su -c 'id'` 返回 `uid=0(root)`，Root **实际可用**。

**原因**：`M.a()` 用 `ProcessBuilder("su", "-c", ...)` 在 **App 进程内**启动子进程。App 的 SELinux 上下文是 `untrusted_app`，执行 `su` 时被拒绝（errno 13 Permission denied）——这是 KernelSU 的安全设计：必须先在管理器里按**签名**授权该应用。

**由于我们重签了 APK**（`CN=MiDuo Rebuild`），签名与原版不同，KernelSU 里没有对应记录，所以拒绝了。

**这不是代码 bug，是环境授权问题**。如果需要在 App 内真正用上 Root（如「帐篷钟面」「Bug 抓取」等需要 Root 的功能），需要在 KernelSU 管理器里把 MiDuo 加入允许列表。

**不过**：去掉启用限制后，Root 检查不通过**不再影响总开关打开**，核心功能（桌面布局、外屏比例、侧栏等）走 LSPosed 注入路径，不需要 App 进程内的 su。
