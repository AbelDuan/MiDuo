## 本轮的核心成果：按类作用域解析

第 9 轮遗留 98 个错误，其中 96 个是 `cannot find symbol`。根因是**同一个名字在不同嵌套类里有不同含义**：

```java
// 顶层类 b
private final N e;           // line 736
private static Field e;      // line 226

// 嵌套类 L
final SurfaceControl b_v;    // line 1551  ← 已改名
// 但赋值语句仍是
this.b = surfaceControl;     // ← 47 个错误来自这里
```

`this.b` 在 `L` 内部应指向 `L.b_v`，但文本上写的是 `this.b`。**纯文本替换无法区分"哪个类的 this"**。

### 解法：解析类范围 + 成员表

写了 `scope_fix.py`：

1. 用 tokenizer 剥离字符串/字符字面量后统计大括号深度
2. 建立 67 个类范围 `(name, start, end, depth)`
3. 对每个类，收集**直接成员**（按缩进判定，只算该类自己的字段）
4. 对每条 `this.<f>` 引用，找到它所属的最小类范围，查该类的成员表：
   - 该类声明了 `<f>` → 保持 `this.<f>`
   - 该类声明了 `<f>_v` → 改成 `this.<f>_v`

效果：**98 → 18**。

### 第二阶段：限定常量引用

剩余 18 个里有 16 个是 `dev.duo.workspaceprobe.b.u0` 这类**类限定常量引用**。这些常量已被改名 `u0` → `u0_v`，但限定形式没同步。

统一处理后：**18 → 5**。

### 第三阶段：手工修 3 处

| 位置 | 修法 |
|---|---|
| `this.n = true;`（类 R 内，字段声明是 `n_v`） | → `this.n_v = true;` |
| `this.b = valueAnimator;`（类 C0034c 内，字段是 `b_v`） | → `this.b_v = valueAnimator;` |
| 同上第二处引用 | → `this.b_v` |

结果：**5 → 2**。

## 剩余 2 个错误

都在 `dev/duo/workspaceprobe/b.java` 的 `d0()` 构造器：

```java
2584: boolean b_v = b_v.b(dev.duo.workspaceprobe.b.this.i4);
2604: frameLayout.setBackground(b_v.b(b_v ? -149152738 : -134941450, 64.0f));
```

### 为什么改不动

`d0` 类里有字段 `private final boolean b;`（第 2523 行），我的改名把它变成了 `b_v`，于是构造器里的**局部变量**也被连带改成了 `b_v`，与静态方法 `b(int,float)` 的接收者 `b.b` 冲突。

本轮试了 5 种改法，全部失败：

| 尝试 | 结果 |
|---|---|
| 局部 `b_v` → `bLocal` + 全限定 `dev.duo.workspaceprobe.b.b(...)` | 2 → **902** |
| 加静态别名方法 `bg(int,float)` + 局部 `bLocal` | 2 → **903** |
| 只改局部名不改调用点 | 2 → 903 |
| 新建外部类 `Bg.java` 转发 | 2 → 547（第 8 轮） |
| 只改 3 行限定形式 | 2 → 547（第 8 轮） |

**根因**：一旦 `d0()` 结构被改动，javac 就会深入检查这个 17,051 行类的其余部分，暴露出约 900 个真实错误。也就是说 `d0` 的 2 个错误仍在**掩盖**约 900 个错误。

这与前几轮的模式完全一致（`T.java` 22 掩盖 314、`workspaceprobe/b` 2 掩盖 547）。
